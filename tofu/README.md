# tofu/

OpenTofu code for the homelab. This README explains how the directory is organized, what modules and environments are, what each file does, and how data moves between them. It is a reference for future me.

## Modules
In this tree, everything under `envs/` is a root module and everything under `modules/` is a child module.

## `modules/`: reusable building blocks

These are child modules. They are never run directly. They contain no provider configuration and no state of their own. They only describe how to build one kind of thing. This directory is a library of reusable recipes.

### `modules/vm/`

Builds exactly **one Proxmox virtual machine** by cloning a template. It is deliberately generic. Everything that varies between machines (name, VM ID, CPU count, memory, disk size, template, network, tags) is an input variable.

### `modules/lab_network/`

Builds the **SDN objects**: a zone, a virtual network (VNet), and a subnet with a DHCP range. It is a separate module because it is a self-contained concern with a small interface. This lets it be developed and tested alone before any VM exists, keeps `vm` generic (the VM module just receives a network name as a string), and allows reuse by a future Linux lab with a different subnet.

### `modules/windows_lab/`

A **composition module**. It does not define VMs itself. It calls `lab_network` once and `vm` several times (once per machine) and wires them together, for example by passing the network created by `lab_network` into each VM. It represents the concept "a Windows lab".

The machines are described by a map variable (name mapped to template, cores, memory, disk, role) and created with `for_each`. Adding a machine is then an edit to the tfvars file, not a new module call.

This layering (primitives, then compositions) allows `vm` to be reused for a Linux lab later without touching the Windows lab.

## `envs/`: concrete deployments

Each subdirectory is a **root module**: one deployable instance of something, with its own settings and its own state.

### `envs/windows_lab/`

The deployment of the Windows lab. A future `envs/linux_lab/` would be a separate deployment with separate state.

## Files inside a child module

Every child module uses the same set of files with the same purposes.

### `variables.tf`

Declares the module's **inputs**. Each `variable` block gives a name, a type, a description, optionally a default, and optionally validation rules. A variable without a default is mandatory: the caller must provide it. This file is the module's public interface, so reading it shows how to use the module.

### `main.tf`

Contains the **resources** and **data sources**: the actual objects being created or looked up.

- In `vm`: the Proxmox VM resource.
- In `lab_network`: the SDN resources.
- In `windows_lab`: mostly `module` blocks calling the other two.

May also contain `locals`: named internal values computed once and reused, such as building a full VM name from a prefix and a role.

### `outputs.tf`

Declares the module's **outputs**: values the caller can read. Since a module's internals are invisible to the caller, anything the caller needs (for example the VM's IP address) must be exposed as an output.

### `versions.tf`

Declares **requirements**: which OpenTofu version the module works with and which providers it needs (name, source, version constraint). It states what the module needs but does not configure it. Configuration such as the Proxmox URL and credentials belongs in the root.

## Files inside a root module (`envs/windows_lab/`)

The root uses the same file types plus a few that only roots have.

### `providers.tf`

Configures **providers**. A provider is the plugin that translates OpenTofu resources into API calls to a specific system. The `bpg/proxmox` provider talks to the Proxmox API. This file sets the endpoint address, authentication method, and TLS settings. Secrets such as the API token should come from environment variables, not from this file.

### `versions.tf`

Pins the OpenTofu version and provider versions. In the root it is also where a backend (where state is stored) and state encryption would later be configured.

### `variables.tf`

Declares the root's inputs: the values that make this deployment specific, such as the Proxmox node name, template IDs, storage names, subnet CIDR, and the map describing the lab machines.

### `terraform.tfvars`

Supplies **values** for the variables. This is what I edit to change the deployment without changing code. It is git-ignored because values are environment-specific and may be sensitive.

### `terraform.tfvars.example`

A committed copy with placeholder values showing which values must be provided. OpenTofu ignores it because its name does not match the automatically loaded patterns.

### `main.tf`

Contains the `module` blocks that call into `../../modules/...`. In the final design this is short: one call to `windows_lab`, passing variables through.

### `outputs.tf`

Re-exposes values from the called modules so that `tofu output` prints them. The root's outputs are the only ones visible at the command line or to other tools such as Ansible.

## Files generated by OpenTofu

### `.terraform/`

Created by `tofu init`. Contains downloaded provider plugins and module metadata. Large and reproducible, so it is git-ignored.

### `.terraform.lock.hcl`

Records the exact provider versions and checksums selected at init time. It is committed so that every future run uses identical provider versions.

### `terraform.tfstate` (and `terraform.tfstate.backup`)

The **state file**, created in the root directory after the first apply. It is OpenTofu's record of which real objects correspond to which resources in the code. This is how `plan` knows what to create, change, or delete.

State can contain secrets in plaintext and must never be committed. OpenTofu has native state encryption, which is worth enabling later.

The names `terraform.tfvars` and `.terraform.lock.hcl` keep "terraform" in OpenTofu for compatibility. Do not rename them.

## How data flows between layers

Inputs flow **down** through the layers, outputs flow **up**. A module never reaches into another module. Everything crosses a boundary through an explicit variable or output.

Example: the VNet name.

1. `lab_network` creates the VNet and exposes its name as an **output**.
2. `windows_lab` reads that output and passes it as an **input** to each `vm` call.
3. `vm` uses that input in the VM's network device setting.

Example: a VM's IP address, travelling the opposite direction.

1. `vm` exposes the IP as an output.
2. `windows_lab` collects the IPs into a map and outputs it.
3. The root outputs it again.
4. It becomes visible with `tofu output`.

Values typed by hand travel down the same path:

```
terraform.tfvars
  -> root variables.tf
  -> root main.tf (module block arguments)
  -> child variables.tf
  -> child main.tf (resources)
```

## Summary of roles

| Location | Role | Has state? | Run commands here? |
|---|---|---|---|
| `modules/vm` | Build one VM | No | No |
| `modules/lab_network` | Build SDN objects | No | No |
| `modules/windows_lab` | Assemble the lab from the others | No | No |
| `envs/windows_lab` | Deploy the lab, configure provider, hold values and state | Yes | Yes |

Mental model: **modules describe how; environments decide what, where, and with which values.** When something is hard to place, ask whether it is a reusable recipe (module) or a specific deployment choice (env).

## Rules to follow

- Never put `provider` blocks inside reusable modules. Modules declare which providers they need in `versions.tf`; the root configures them.
- Commit `.terraform.lock.hcl` and `terraform.tfvars.example`. Never commit state files, `.terraform/`, or `terraform.tfvars`.
- Keep credentials (the Proxmox API token) in environment variables, never in files in the repository.
- Give variables a `type` and a `description`, and use `validation` blocks where a mistake can be caught at plan time.
- Keep module nesting shallow. Two levels (`windows_lab` calling `vm`) is usually enough.
- Use `for_each` rather than `count` for sets of similar objects, because `for_each` keys are stable when items are added or removed.
- When renaming a module call or moving a resource between modules, use a `moved` block so OpenTofu keeps the existing object instead of destroying and recreating it.

## Dependencies outside this directory

This code assumes the following already exist (built outside of this directory):

- A working Proxmox host with a dedicated API user, role, and token, and the storage definitions used by the code.
- A DHCP-capable SDN setup on the host (dnsmasq) if DHCP is used on the lab subnet.
- Generalized (sysprepped) Windows Server templates, one for Desktop Experience and one for Server Core, cloned by the `vm` module.

Host bootstrap is planned as Ansible work, and template building as Packer work. Neither is part of this directory.
